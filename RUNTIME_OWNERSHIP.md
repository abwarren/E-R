# RUNTIME OWNERSHIP — W4P PLO Poker Platform

**Status:** CANONICAL — permanent reference, not an investigation
**Created:** 2026-07-03
**Source:** 63,329 live snapshots + AUTHORITY_MODEL.md + ARCHITECTURE_BASELINE.md
**Rule:** Every code change MUST reference this document. No new heuristic may be introduced without updating the ownership model.

---

## 0. Runtime Invariants

These are not guidelines. They are permanent architectural rules. Every future change is measured against them.

### I1 — Identity

> Every runtime object belongs to exactly one `hand_id`.

A runtime object must never represent two hands simultaneously. When a new hand begins, the old hand is archived, not merged.

### I2 — Authority

> Structural fields may only be modified by `is_authoritative_snapshot()`.

No other code path may decide structural ownership. No `if available_actions:` gate. No `if hero_active:` heuristic. One function. One authority.

### I3 — Selection

> Consumers receive one coherent structural view.

The selector must never synthesize a table from multiple competing structural snapshots. It picks the best entry from `_tables` — it does not merge entries.

### I4 — Action Ownership

> Exactly zero or one player owns the action at any instant.

`action_owner` is `null` OR one seat. Never two. Never three. If multiple seats report poker actions simultaneously, the data is inconsistent — log the conflict, pick one, do not present both.

## 1. Public Runtime Model

Exposed via `_table_view()` in every API response:

```json
{
  "hand_id": "339aec5c-e800-4a00-9e0c-a3f28e5b6232",
  "table_id": "pb_2589955",
  "street": "FLOP",
  "board": {"flop": ["2s","3s","4s"], "turn": null, "river": null},
  "pot_zar": 40,
  "dealer_seat": 1,
  "state_version": 1372,
  "last_updated": 1783051219.7516723,
  "seats": [ ... ],

  "authority": {
    "source_bot": "monarchi",
    "reason": "board_present"
  },

  "action_owner": {
    "seat": 4,
    "name": "monarchi",
    "actions": ["fold", "call", "raise"]
  }
}
```

**`authority` and `action_owner` are different concepts.** The authoritative snapshot might come from Bot A while the action currently belongs to Seat 6. They are never the same field.

### 2.1 Authority (Computed Projection)

Exposed as `authority` in the public runtime model. Never written by any snapshot. Never persisted. Derived from the most recent authoritative snapshot.

| Field | Owner | Source | Mutable |
|-------|-------|--------|---------|
| `authority.source_bot` | Backend | `bot_id` of the entry that last passed `is_authoritative_snapshot()` | Yes |
| `authority.reason` | Backend | Which signal granted authority (`poker_actions`, `street_advanced`, `cards_and_pot`, `board_present`) | Yes |

### 2.2 Action Owner (Computed Projection)

Exposed as `action_owner` in the public runtime model. Never written by any snapshot. Never persisted. Derived from the current per-seat `available_actions`.

| Field | Owner | Source | Mutable |
|-------|-------|--------|---------|
| `action_owner.seat` | Backend | Computed from all per-bot entries | Yes |
| `action_owner.name` | Backend | Computed from seat at `action_owner.seat` | Yes |
| `action_owner.actions` | Backend | Computed from `available_actions ∩ POKER_ACTIONS` | Yes |

**Rule:** Only `{fold, check, call, bet, raise, all_in}` confer action ownership. `back_to_game`, `resume_hand`, `show`, `run_it_twice` do NOT. If no seat has poker actions, `action_owner` is `null`. If multiple seats have poker actions (should never happen — violates I4), the first found wins and a warning is logged.

## 5. Authority Function

`is_authoritative_snapshot(snapshot)` is defined ONCE in `backend/app.py`.

**Signals (any one is sufficient):**

| # | Signal | Condition |
|---|--------|-----------|
| S1 | Hero has poker actions | `available_actions ∩ {fold, check, call, bet, raise, all_in} ≠ ∅` |
| S2 | Street advanced past PREFLOP | `street ∈ {FLOP, TURN, RIVER}` |
| S3 | Dealt in with blinds | `hole_cards present AND pot_zar > 0` |
| S4 | Board has visible cards | `board.flop is non-empty` |

No other component may implement a version of this rule. Consumers trust the backend's decision.

## 6. Seat Merge Rules

When seat `sno` is updated by bot `incoming_bot`:

| Seat Owner | Incoming Bot | Merge Behavior |
|-----------|-------------|---------------|
| `incoming_bot` | `incoming_bot` | Full replace — all fields from snapshot |
| Different bot | `incoming_bot` | Metadata update: `stack_zar`, `status`, `is_dealer`, `last_seen`, `hole_cards` (observed). Identity fields PROTECTED. |
| None (unowned) | `incoming_bot` | Full replace — incoming bot claims ownership |

Identity fields (never overwritten by another bot): `name`, `is_hero`, `is_active`, `available_actions`, `bot_id`.

## 7. Hand Lifecycle

| Event | Authority | Action |
|-------|-----------|--------|
| New table entry created | Backend | Generate `hand_id` (UUID4), return in POST response |
| Extension echoes same `hand_id` | Extension | No change — same hand continues |
| Extension echoes different `hand_id` | Extension | Archive old hand, start new hand (Phase B+) |
| Same bot's street regression | Authoritative snapshot | New hand detected (legacy path) |
| Different bot's street regression | Not authoritative | Blocked by multi-bot guard |
| Table entry empty for 60s+ | Backend cleanup | Entry removed from `_tables` |
| Seat not seen for 30s+ | Backend cleanup | Seat evicted, ownership cleared |

## 8. Consumer Rules

| Consumer | May Decide | Must Never Decide |
|----------|-----------|-------------------|
| Remote UI | Render state, re-render on change | Seat assignment, hand identity, structural field values |
| Engine | Extract cards for equity, trigger calculation | Hand identity, which hand is "correct" |
| Extension | Scrape DOM, build snapshot, echo hand_id | Which fields are authoritative, structural field ownership |

## 9. Permanent Rules

1. `is_authoritative_snapshot()` lives in ONE place — `backend/app.py`.
2. No heuristic may be introduced without updating this document.
3. No component may implement its own version of the authority rule.
4. Every code change that touches structural fields or hand identity MUST reference this document.
5. `available_actions` alone is NEVER used to decide structural field authority.
6. `back_to_game` is NOT a poker action and does NOT confer authority.

### 9.1 Regression Rule

> Every runtime field must have exactly one owner, one producer, and one semantic meaning.

If a future PR causes a field to answer two different questions, it is rejected during review.

| ❌ Rejected | Why |
|------------|-----|
| `hero_active` = "can act" AND "owns structural state" | One field, two meanings |
| `available_actions` = "buttons shown" AND "current table authority" | One field, two meanings |
| `last_ts` = "freshness" AND "action priority" | One field, two meanings |

Every field answers exactly one question. If a new question arises, add a new field. Never overload.

### 9.2 Four Invariant Gate

Before merging any change to `backend/app.py` or `source/`, verify:

| Invariant | Check |
|-----------|-------|
| I1 — Identity | Does every runtime object belong to exactly one `hand_id`? |
| I2 — Authority | Is `is_authoritative_snapshot()` the ONLY path that writes structural fields? |
| I3 — Selection | Does the selector produce one coherent view, never a merge of competing snapshots? |
| I4 — Action Ownership | Is `action_owner` always `null` or exactly one seat? |

Any change that violates an invariant is rejected. The invariant is amended first (with an ADR), then the code follows.
